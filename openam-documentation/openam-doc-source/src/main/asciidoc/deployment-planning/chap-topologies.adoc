[#chap-topologies]
== Example Deployment Topology

This chapter shows how to deploy OpenAM 16.x behind a reverse proxy and load balancer. xref:#openam-sites[Sites] describes a single-site deployment. xref:#multi-sites[Multiple Sites] covers the additional decisions for operating across data centers.

[#logical-topology]
=== About the Example Topology

The public tier accepts browser and API requests on a stable HTTPS endpoint. Behind that tier, OpenAM provides identity services and runs in a dedicated server pool. Protected applications can enforce policy through an agent or gateway where the integration requires it. Keep the directory and token stores on a restricted network.

xref:#figure-active-openam-deployment[OpenAM Deployment Example] illustrates these paths. The components represent roles that existing load balancers, proxies, and application platforms can fill.

[#public-tier]
=== The Public Tier

The public tier provides an extra layer of security with a DMZ consisting of load balancers and reverse proxies. This section presents the DMZ elements.

[#gslb]
==== The Global Load Balancer

A global load balancer or DNS traffic manager directs clients to a healthy site. For a DNS-based design, recovery time includes health detection and the time clients and recursive resolvers continue using cached answers. Use a stable public URL and test failover and failback with representative clients. Choose site affinity where it improves locality and verify that clients can still reach the other site when a site fails.

[#frontend-lbs]
==== Front End Local Load Balancers

A site load balancer distributes requests across healthy OpenAM nodes. Deploy the load balancing layer redundantly and use health checks to remove unavailable nodes from service. A TCP connection check confirms that the port is listening. The OpenAM xref:../admin-guide/chap-monitoring.adoc#is-openam-alive[`isAlive.jsp` check] also checks access to the configuration store. From outside the node, run separate synthetic checks against critical paths such as login, token issuance, and authorization to cover dependencies such as identity and CTS stores and upstream identity providers.

Choose check intervals, timeout and recovery thresholds, and draining behavior for maintenance. In an orchestrated environment, distinguish startup, readiness to receive traffic, and process liveness so that a shared datastore outage does not cause unnecessary restarts.

[#reverse-proxies]
==== Reverse Proxies

Route only the endpoints required for each integration through the public proxy, including UI assets and selected protocol callbacks. Restrict administration, monitoring, installer, and management endpoints to authorized access paths. Apply cache rules to static assets as permitted by their response headers. Keep authentication, session and token responses out of shared caches. See xref:../how-to/how-to-restrict-xui-access-with-a-reverse-proxy.adoc#how-to-restrict-xui-access-with-a-reverse-proxy[Restrict XUI Access with a Reverse Proxy] for XUI routes.

At the trusted edge, replace incoming forwarding headers with values derived from the connection and intended public endpoint. Configure the container and OpenAM to accept this information only from trusted proxies, and restrict direct client access to the backend. Align the public scheme, hostname, port and context path with the site URL and with the settings used to generate URLs. In a deployment that publishes a single fixed URL, configure the xref:../admin-guide/chap-openid-connect.adoc#configure-base-url-source[Base URL Source] where the protocol uses it. Validate issuer and redirect URLs, cookies, and callbacks at the public URL. See xref:../install-guide/chap-install-multiple.adoc#handle-request-headers[Handling HTTP Request Headers] and xref:../admin-guide/chap-securing.adoc#protect-network-access[Protecting Network Access].

[#openig]
==== OpenIG

OpenIG is a separately released identity gateway. Use it to protect applications through OpenAM and to integrate applications that cannot enforce access policy directly. OpenIG routes and filters HTTP requests and responses, and can perform authentication or policy integration on behalf of the application.

Select the OpenIG release and runtime using the link:https://doc.openidentityplatform.org/openig/gateway-guide/chap-install[OpenIG installation guide]. If the gateway is on a critical request path, include it in the availability design, health checks and capacity tests.

[#ssl-termination]
==== TLS Termination

Use HTTPS for public access. At a TLS-terminating load balancer or proxy, establish a new TLS connection to the backend and verify the backend certificate and hostname. With TLS pass-through, the next hop terminates TLS. A layer 4 pass-through load balancer cannot inspect HTTP cookies. If you need cookie affinity, apply it at the layer 7 hop that can read the request.

Set and test the cookie domain, `Secure`, `HttpOnly` and `SameSite` settings against your actual browser flows. Include cross-site POST callbacks for SAML and CDSSO and redirects for OpenID Connect (OIDC) when those integrations are in use.

[#about-the-app-tier]
=== About the Application Tier

The application tier hosts OpenAM and the protected applications. Agents and gateways intercept access to protected resources and enforce decisions based on authentication and policy. Register the URL that each client uses to reach OpenAM and plan the routes from browsers, agents, and servers. For the OpenAM runtime, see xref:chap-hw-sw-requirements.adoc#chap-hw-sw-requirements[OpenAM Hardware and Software Requirements].

[#figure-app-svr-deployment]
image::images/app-svr-deployment.png[Protected applications with policy agents accessing OpenAM]

Plan balancing for both the authentication exchange and the session that follows it.

* *Authentication in progress*. An authentication exchange can retain state in the node handling it, even when the realm issues stateless sessions after login. Route all steps of a multi-request flow to the same node where the flow requires it. Test browser and REST callbacks before relying on a specific affinity mechanism. If that node fails mid-flow, the client may need to restart authentication.
* *Established stateful session*. A node retrieves the persisted session from the shared Core Token Service (CTS) if its local cache does not hold it. Cookie affinity can improve cache locality. For clients using the OpenAM load-balancer cookie, `amlbcookie` by default, map each node's unique value to that node. Serve requests without a usable mapping, including REST requests that send an SSO token in a header, through a healthy node.
* *Established stateless session*. Any node with compatible session settings and cryptographic material can process a valid client-held session token. When stateless-session revocation is configured, the denylist uses CTS. See xref:../admin-guide/chap-session-state.adoc#chap-session-state[Configuring Session State].

[#openam-agents]
=== OpenAM Policy Agents

Policy agents enforce access to protected resources. Choose the agent type and version for the protected application's server. Check compatibility for both that runtime and the OpenAM release. Plan the agent profile, notification and policy traffic, cache behavior, and high availability of the public endpoints that agents and browsers use.

When using SSO or CDSSO, test redirects, session expiry, logout, and behavior when OpenAM or the network is unavailable. For public paths that bypass enforcement, document and test the exceptions.

[#openam-web-policy-agents]
==== Web Policy Agents

A Web Policy Agent is a native Web server plugin that intercepts requests for protected resources. See the xref:../web-users-guide/index.adoc[Web Policy Agent Guide].

[#j2ee-policy-agents]
==== Java EE Policy Agents

A Java EE Policy Agent integrates with the application server and uses a servlet filter to enforce access to the protected application. Verify the integration steps and the servlet API expected by the agent release with the xref:../jee-users-guide/index.adoc[Java EE Policy Agent Guide].

[#openam-sites]
=== Sites

A site groups OpenAM servers under a common entry URL and a load balancing layer. A production site uses redundant OpenAM nodes and load balancers across the failure domains it must tolerate. Plan the configuration, identity, and CTS stores so that the surviving nodes can reach their dependencies after a failure.

Test service failover and session continuity separately. The load balancer can route new requests to healthy nodes after a failure. An established stateful session can continue on a surviving node if a usable copy is available in CTS. An interrupted request may need to be repeated, and a user without a recoverable session may need to sign in again. See xref:../install-guide/chap-session-failover.adoc#chap-session-failover[Setting Up OpenAM Session Failover].

image::images/active-app-tier-deployment.png[OpenAM application tier with a pool of nodes]

A single load balancer can be sufficient for a pilot. For production, size the remaining nodes and network links to serve peak traffic during loss of a node or of a load balancer.

[#multi-sites]
==== Multiple Sites

Choose whether users must retain existing sessions if a whole site fails. A design can route traffic to another site and require users to authenticate again. Cross-site continuity for established stateful sessions requires sites in the same OpenAM deployment. The surviving site must recognize the IDs of the server and site that issued the session and access a usable copy of the record in the same logical CTS. Directory replication is configured separately and can lag during normal operations or a WAN outage. Verify reachability and currency for CTS and all other required stores, integration endpoints, and keys.

Use consistent public URLs, cookie scope, issuer identifiers, and partner settings across the sites that handle the same traffic. Measure recovery time and acceptable data loss for configuration, identity and token data. Test site loss, WAN partition and failback under load, including recent logins and revocations. Size each site to absorb the traffic it will receive after failover.

[#backend-ds]
=== Back End Directory Servers

OpenAM uses three logical stores. Choose their backends, capacity, redundancy, backup, and failure behavior independently. A single embedded OpenDJ instance can provide all three roles for an evaluation. In production, size each role and decide which roles require separate stores or operational ownership.

* *Configuration store*. Embedded or external OpenDJ holds OpenAM configuration, including realms, authentication and policy settings, and federation metadata and key aliases. If using embedded OpenDJ for a multi-server site, configure replication when adding nodes and plan for application and directory outages in the same failure domain. An external configuration store has a lifecycle independent of OpenAM and can be sized and operated separately. See xref:../install-guide/chap-prepare-install.adoc#install-prepare-opendj-external-config-store[Preparing External OpenDJ for Configuration Data].
* *Identity store*. Choose a backend per realm according to your source of identities and the operations your integrations need, including credentials, group lookup, schema, and any required write access. OpenAM provides LDAP and JDBC integrations. See xref:../install-guide/chap-prepare-install.adoc#prepare-identity-repository[Preparing an External Identity Repository] and xref:../admin-guide/chap-realms.adoc#chap-realms[Configuring Realms].
* *CTS*. Plan for the read and write load of stateful sessions, OAuth tokens, and other token or revocation data used by the services you enable. An external CTS store lets you size and replicate this load independently. For an external OpenDJ CTS store, supply the directory server addresses to OpenAM directly and use its active/passive or token affinity configuration. A generic LDAP load balancer can send a read to a replica before the corresponding write arrives. Even with ordered failover, allow for replication lag across replicas. See xref:../install-guide/chap-cts.adoc#cts-general-recommend[Configuring the Core Token Service].

Apache Cassandra is an optional backend for the identity store and CTS. See xref:../how-to/how-to-use-apache-cassandra-as-user-and-session-datastore-in-openam.adoc#how-to-use-apache-cassandra-as-user-and-session-datastore-in-openam[Using Apache Cassandra as a User and Session Data Store].

Provision each OpenAM node with the key material, keystore passwords, trust settings, and any shared secrets its deployment requires. Replicating SAML configuration and key aliases does not provision the private keys. Include those keys in deployment, backup, and rotation plans, and verify both sites can complete federation transactions. See xref:../admin-guide/chap-certs-keystores.adoc#chap-certs-keystores[Managing Certificates and Keystores].

[#realms]
=== Realms

Realms organize users and applications within one OpenAM deployment. They provide configuration boundaries for authentication, identity repositories, authorization, federation and delegated administration.

Realms in a deployment share server processes and deployment infrastructure. When a tenant requires an independent failure domain, upgrade schedule or security boundary, evaluate separate OpenAM deployments. See xref:../admin-guide/chap-realms.adoc#chap-realms[Configuring Realms].
