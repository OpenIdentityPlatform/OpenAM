== Sizing Hardware and Services for Deployment

ifdef::env-site[]
anchor:chap-sizing[]
endif::[]

Size OpenAM, its data stores, and the network paths between them against the workloads and failure scenarios in your deployment plan.
Use measurements from the target release and topology, including external authentication providers, policy agents, gateways, and replicas.

[#size-for-availability]
=== Sizing for Availability

Define which operations must continue during a component failure and how long a disruption can last.
Set a recovery time objective (RTO) and a recovery point objective (RPO) for each service or class of data.
Record whether users must retain established sessions or can sign in again.
Test any acceptable degradation, such as restarting an authentication flow that was in progress on a failed node.

Site membership organizes OpenAM servers for routing.
Configuration, identity data, and CTS tokens are replicated by their respective data stores according to the selected topology.
A surviving site can recover an established stateful session when it can read the required session state from CTS and receives the corresponding client session reference.
Measure data availability, replication lag, and routing delays independently.
See xref:chap-topologies.adoc#multi-sites[Multiple Sites].

Size the surviving components to meet the required service levels during outages and maintenance.
For example, if a representative load test shows that an OpenAM node can sustain 500 requests per second at the target latency and error rate, three equally sized nodes leave a nominal 1,000 requests per second with one node out of service.
Verify the actual capacity with one node out of service and under uneven load.
Include the impact of cold caches, retries, and LDAP/CTS connection failover in that test.

If a second site is required, calculate the traffic it must take over, including traffic that was originally served by that site.
Allow for DNS caching, the time to detect a failure, replication during recovery, and the load when the failed site returns.

[#size-for-service-levels]
=== Sizing for Service Levels

For each workload, record steady and peak throughput, concurrency, response-time objectives (such as p95 and p99), and the acceptable error rate.
List external calls and their latency, retries, and timeout budgets.
For example, a deployment might require 95% of sign-in requests to finish within one second at a peak of 25,000 sign-ins per hour.
Use an explicit definition of sign-in completion, including any external identity provider and MFA work that counts toward the objective.

[cols="1,2",options="header"]
|===
|Workload |Inputs to capture

|Authentication
|Concurrent sign-ins, chain and MFA steps, directory lookups, and identity provider latency. Separate in-progress authentication from established SSO sessions.

|Session validation and policy evaluation
|Concurrent sessions, validation and authorization rates, realms, policy complexity, session idle and maximum lifetimes, and cache hit rates. Record logout and expiration rates.

|OAuth 2.0 and federation
|Authorization requests, token issuance and refresh rates, revocation, lifetimes, signing and encryption settings, and the partner and client mix.

|Data stores and audit
|CTS create, read, update, and delete rates and queue latency. Include identity and configuration operations, replication lag, audit events, and volume during troubleshooting.
|===

Estimate the number of live tokens separately for each type.
For a steady flow of 100 tokens per second with a ten-minute lifetime and no early removal, roughly 60,000 such tokens coexist.
If a representative token occupies 5 kB of logical storage, that is about 300 MB of token data per full replica before indexes, change logs, database overhead, backups, and bursts.
Measure those costs in the selected data store.
Use actual CTS operations to estimate replication traffic, and measure token cleanup under sustained load.
A serialized token's size provides no estimate of the retained JVM heap per cached session.

Use representative configuration, policies, profiles, token lifetimes, and a realistic load mix.
Run tests at steady load, through bursts, after node replacement, and while a component is unavailable.
Record p95 and p99 latency, error rate, and dependency saturation for each critical operation so that you can locate capacity limits.
See xref:chap-deployments.adoc#plan-service-performance-tests[Planning Service Performance Testing].

[#size-systems]
=== Sizing Systems

Record a sizing budget for each OpenAM node, each directory or token store replica, each proxy or load balancer, and all network links.
Recheck the budgets when the workload, versions, topology, or retention settings change.

[#size-cpu-memory]
==== Sizing System CPU and Memory

Measure CPU spent on authentication modules, policy evaluation, signing, and encryption, including the cost of validating JWTs if you use stateless sessions.
Measure retained heap with representative live sessions and caches, as well as allocation rates and garbage-collection pauses under peak and sustained load.
Budget process memory outside the Java heap, including metaspace, thread stacks, direct buffers, and other native memory.
For containers, check the JVM heap, total process memory, and memory limit together. Allow for the application's working set and restarts under load.

An embedded OpenDJ instance shares the OpenAM JVM and adds directory database cache and processing demand.
When the directory is external, size and monitor its process independently.
Select heap and directory cache settings for the target build and workload.
See xref:chap-hw-sw-requirements.adoc#ram-requirements[Memory Requirements] and xref:../admin-guide/chap-tuning.adoc#chap-tuning[Tuning OpenAM].

[#size-network-connections]
==== Sizing Network Connections

Account for client traffic, directory and CTS operations, agent and server notifications, external authentication calls, and replication.
Measure request and response sizes at each tier. Include cookies and headers, especially for stateless sessions and federation traffic.

Measure link utilization and replication lag across sites at peak traffic and while recovering an unavailable replica.
Test connect and read timeouts for a slow dependency, and allow for retries and replication backlog when estimating available bandwidth.

[#size-io-storage]
==== Sizing Disk I/O and Storage

Measure the space for the packaged and deployed application, persistent configuration, keys, and any embedded directory data.
For external stores, include data, indexes, replication change logs, temporary maintenance space, and backups in the budget for each replica.
Measure write operations per second and storage latency during token creation, expiration and cleanup, log spikes, and restoration or replica catch-up.

Budget audit and debug logs from measured rates, retention, and space for rotation.
Configure alert thresholds for remaining space and sustained I/O latency.
See xref:chap-hw-sw-requirements.adoc#storage-requirements[Disk Storage Requirements] and xref:../admin-guide/chap-monitoring.adoc#chap-monitoring[Monitoring OpenAM Services].
