== OpenAM Hardware and Software Requirements

ifdef::env-site[]
anchor:chap-hw-sw-requirements[]
endif::[]

Select a target OpenAM release, a deployment package, and a data store for each role before sizing the deployment. Use the release requirements for compatibility and xref:chap-sizing.adoc#chap-sizing[Sizing Hardware and Services for Deployment] to validate resource estimates under load.

[#hardware-requirements]
=== Hardware Requirements

[#storage-requirements]
==== Disk Storage Requirements

[#storage-requirements-server]
===== Server Disk Storage Requirements

Budget for the downloaded package, the deployed WAR and any expanded copy, container work and temporary files, and the previous version and staging space needed during an upgrade. Measure the actual files from the target release. For example, the OpenAM 16.1.4 WAR alone is about 293 MB and its full distribution ZIP is about 1 GB.

Allow separate capacity for the configuration directory, embedded directory data and replication logs if used, backups, and audit, debug, and container logs. The default CSV audit handler writes to `<configuration-base>/<context>/log/`. Debug logs default to `<configuration-base>/<context>/debug/`. Set rotation, retention, and collection for each destination. Allow for diagnostic logging during an incident. See the xref:../admin-guide/chap-audit-logging.adoc#chap-audit-logging[Audit Logging] and xref:../admin-guide/chap-monitoring.adoc#debug-logging[Debug Logging] chapters.

Use storage that meets the directory server's file ownership, locking, and durability requirements for embedded database files. Network file systems such as NFS cannot guarantee the exclusive access OpenDJ requires. Check throughput, free space, and file descriptor limits under peak traffic and during replication catch-up and backups. See https://doc.openidentityplatform.org/opendj/admin-guide/chap-tuning[OpenDJ storage guidance] and xref:../install-guide/chap-prepare-install.adoc#prerequisites-file-descriptors[Setting Maximum File Descriptors].

[#storage-requirements-pa]
===== Policy Agent Disk Storage Requirements

Size for the selected agent release, local logs, and the diagnostic log volume expected during an incident. For each agent, determine how it collects audit events and who manages log retention.

[#storage-requirements-openig]
===== OpenIG Disk Storage Requirements

Measure the selected https://github.com/OpenIdentityPlatform/OpenIG/releases[OpenIG release] and include the deployed application or container image, configuration, and logs. Include capture and script logging in diagnostics tests and budget retention at the configured log sink.

[#storage-requirements-recommendations]
===== Disk Storage Recommendations

Measure the sustained write rate and peak space use for each directory and log destination. Include replication backlog, backups, retention, and room to stage a restore. Confirm that alerts and rotation operate before a volume fills and that disk latency stays within the service targets during a long-running load test.

[#ram-requirements]
==== Memory and CPU Requirements

Size the JVM heap from the measured working set at peak traffic. Embedded OpenDJ runs in the OpenAM JVM, so include its backend cache and other directory activity in the measurement. With a separate directory server, size and monitor that process separately.

Budget memory beyond the heap for thread stacks, metaspace, direct buffers, the JVM and container, and the file system cache. In a container, leave room between the heap maximum and the container memory limit. Check resident memory, allocation rate, garbage collection pauses, and CPU throttling under sustained and burst traffic. Choose heap settings based on the target JDK, collector, and workload, then verify latency with a node unavailable.

[#hw-and-sw-requirements]
=== Software Requirements

[#os-requirements]
==== OpenAM Operating System Requirements

anchor:am-os-requirements[]
Select a maintained operating system and processor architecture supported by the selected JDK, web container or container runtime, and any native agents or libraries you install. Record the exact combinations used for acceptance tests.

[#sec-java-requirements]
==== Java Requirements

anchor:am-java-requirements[]
Choose a JDK release accepted by both OpenAM and the web application container. See xref:../release-notes/requirements-and-upgrade.adoc#release-requirements[Requirements and Upgrade Considerations] for the release matrix and xref:../install-guide/chap-prepare-install.adoc#prepare-java[Preparing a Java Environment] for the required module export options when running the WAR.

[#web-container-requirements]
==== OpenAM Web Application Container Requirements

anchor:am-web-containers[]
Use the container and Java combinations listed in xref:../release-notes/requirements-and-upgrade.adoc#release-requirements[Requirements and Upgrade Considerations]. The OpenAM WAR uses Jakarta APIs from release 16.0.3. Validate custom filters, listeners, and other servlet extensions when moving from a Java EE deployment. Give the web container's service account write access to the designated OpenAM configuration directory and the container's work and temporary directories.

[#container-deployments]
==== Container Deployments

Use a versioned image and record its digest for repeatable deployment. Use a stable server identity, public hostname, and context path. The project image uses `/usr/openam/config` for OpenAM configuration by default. Persist that directory outside the container, give each instance its own writable directory, and verify that a replacement instance can start with the intended configuration. Plan external store persistence and backups separately. See xref:../how-to/how-to-persist-openam-docker-container-data-between-restarts.adoc#how-to-persist-openam-docker-container-data-between-restarts[Persist OpenAM Container Data].

For orchestration, plan startup and readiness probes, a process-level liveness check, resource requests and limits, and controlled node replacement. Use the xref:../how-to/how-to-run-openam-in-kubernetes.adoc#how-to-run-openam-in-kubernetes[Kubernetes walkthrough] to evaluate setup on Minikube. For a production deployment, review xref:chap-topologies.adoc#chap-topologies[deployment topology] and the xref:chap-high-level-start.adoc#chap-high-level-start[deployment checklist].

[#data-store-requirements]
==== Data Store Requirements

Select a back end independently for each data role. Where roles initially share a directory, account for the impact of directory maintenance and outages on every dependent service.

[#table-data-store-requirements]
.Data Store Options by Role
[cols="1,2,3",options="header"]
|===
|Role |Options |Planning Checks

|Configuration
|Bundled OpenDJ or external OpenDJ
|Include OpenAM settings, realms, and policies in the backup and recovery plan. For example, the bundled OpenDJ version in OpenAM 16.1.4 is 5.2.0. For external OpenDJ, validate the target release, schema and index setup, and replication. See xref:../install-guide/chap-prepare-install.adoc#prepare-configuration-store[Preparing a Configuration Store].

|Core Token Service (CTS)
|The configuration store's OpenDJ instance by default, a separate OpenDJ store, or the Cassandra CTS integration
|Measure session and token writes, expiry and cleanup rates, and availability during node or store failure. A deployment with stateless sessions can still use CTS for other token data or logout blacklisting. See xref:../install-guide/chap-cts.adoc#chap-cts[Configuring the Core Token Service].

|User identities
|Bundled or external OpenDJ, a directory with the appropriate LDAP identity repository plugin such as Active Directory, or a JDBC or Cassandra identity repository
|Verify the provider version and plugin for the required schema, indexes, search, bind, and write operations. Plan the access rights needed for those operations. See xref:../install-guide/chap-prepare-install.adoc#prepare-identity-repository[Preparing an Identity Repository].

|UMA data, where used
|Default stores or dedicated external stores for UMA resource sets and audit information
|Plan storage, access, and recovery for the parts of UMA used in the deployment. See xref:../admin-guide/chap-uma.adoc#to-configure-uma-external-rs-store[Configuring the UMA Resource Sets Store].
|===

See xref:../how-to/how-to-use-apache-cassandra-as-user-and-session-datastore-in-openam.adoc#how-to-use-apache-cassandra-as-user-and-session-datastore-in-openam[Using Cassandra for User and Session Data] for the Cassandra schema and integration example. Verify all required operations against the exact backend version before relying on an external store in production.

[#sec-supported-clients]
==== Browser and Client Compatibility

anchor:am-supported-clients[]
Choose maintained browser and OS versions for your user population. Verify sign-in, sign-out, redirects, and session renewal on those versions through the production proxy and cookie configuration. Include cross-origin SAML, OIDC, or CDSSO flows, embedded pages, and WebAuthn where used. Record required browser policies, mobile variants, and the outcomes of your checks. Verify native and service clients against the protocol flows and library versions they will use.

[#jee-pa-platform-requirements]
==== Java Policy Agent Requirements

anchor:table-jee-pa-platform-requirements[]
Consult the https://github.com/OpenIdentityPlatform/OpenAM-JEE-Agents/releases[Java policy agent releases] for the selected agent. Verify its JDK and target servlet container combination, the Java EE or Jakarta namespace required by that combination, and interoperability with your OpenAM release.

[#web-pa-platform-requirements]
==== Web Policy Agent Requirements

anchor:table-web-pa-platform-requirements[]
Consult the https://github.com/OpenIdentityPlatform/OpenAM-Web-Agents/releases[Web policy agent releases] for the relevant web server, OS, architecture, and native library dependencies. Use a currently maintained web server and verify the agent against the exact build you deploy. Check TLS trust, agent registration, policy enforcement, and access after OpenAM failover.
