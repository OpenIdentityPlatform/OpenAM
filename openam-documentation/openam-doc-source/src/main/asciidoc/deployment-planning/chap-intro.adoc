[#chap-intro]
== Introduction to Deployment Planning

OpenAM provides authentication, session management, authorization, and federation. A deployment plan identifies the applications and users it serves, the protocols they use, and the infrastructure that keeps those services available. Start by selecting the integrations you need and identifying the dependencies each adds.

[#understanding-iam]
=== Understanding Identity and Access Management

Identity management covers provisioning, updating, and retiring user identities. Access management verifies identities, establishes sessions, and decides which resources those identities can access. Plan which system owns user lifecycle changes, which stores OpenAM reads or writes, and how account or entitlement changes propagate.

[#not-just-sso]
=== Choose How Applications Integrate

anchor:figure-irm[]
For each application, record its protocol, role, public URL, and the component that enforces access. Select the services required for each integration.

[cols="1,2",options="header"]
|===
|Integration |Deployment Decisions

|OpenID Connect and OAuth 2.0
|Choose OIDC for application sign-in and OAuth 2.0 for delegated API access where the clients support them. Define issuer URLs, clients, redirect URIs, scopes, token lifetime, and signing key rotation.

|SAML 2.0
|Choose the identity provider and service provider roles and agree on metadata, signing and encryption keys, attribute mapping, and logout behavior with each partner. Use the Fedlet where a lightweight SAML service provider meets the application requirements.

|OpenAM policy enforcement
|Use a compatible Java or web policy agent where the application environment can host it, or evaluate OpenIG as a gateway for an application protected through a proxy. Decide which realm and policies apply to the protected resources.

|Browser single sign-on
|Plan the session and cookie domains for applications relying on the OpenAM session. Verify CDSSO with the selected agent and browser configuration where applications span domains.
|===

Select authentication chains and factors for the populations you serve, then include any external directory, identity provider, or MFA service in availability and performance testing. OpenDJ can provide directory storage, and OpenIDM and OpenICF can manage identity lifecycle and integrations when those functions are required. Review the xref:../admin-guide/index.adoc[Administration Guide] for configuration details.

[#am-server-overview]
=== OpenAM Server Overview

anchor:figure-openam-apis[]
The OpenAM server exposes protocol endpoints and REST interfaces, the end-user sign-in UI, and administration through a console or command-line tools. A deployment may include load balancers, proxies or agents, and configuration, token, and identity stores. Use xref:chap-topologies.adoc#chap-topologies[Example Deployment Topology] to map the services and their network boundaries. See xref:chap-hw-sw-requirements.adoc#data-store-requirements[Data Store Requirements] for the choices by role.

anchor:table-openam-distribution-files[]
The main OpenAM WAR includes the server and the administration console. The server-only WAR supports deployments that omit the console, which is also published as a separate artifact. The project publishes an OpenAM image for container deployments. See xref:../release-notes/index.adoc[Release Notes] and xref:../install-guide/chap-prepare-install.adoc#download-openam-software[Obtaining OpenAM Software] for the release assets and archive contents.

The full distribution ZIP includes the main server WAR, Client SDK and examples, Fedlet, IdP Discovery, SOAP STS, and command-line tools. The Client SDK is a Java library. Fedlet is a lightweight SAML 2.0 service provider package. Check the target release for the artifact you intend to use and validate any custom extensions against that release.

[#key-benefits]
=== Plan the Deployment Boundaries

Decide which requests are public, which endpoints are reserved for operators, and where identity and token data must reside. Before sizing the deployment, document the required authentication and policy flows, workload and response-time targets, and what should still work if an OpenAM instance, a dependency, or a site fails. Use the xref:chap-deployments.adoc#chap-deployments[deployment architecture chapter] to turn those decisions into a deployment plan.
