[#chap-legacy-servers]
== Migrating Legacy Servers

Use a parallel deployment and migrate manually when you cannot verify an upgrade path from your current release to the target release. This may apply to OpenSSO, Sun Access Manager, and older OpenAM deployments. See xref:chap-about-upgrades.adoc#sec-supported-upgrades[Upgrade Paths].

For complex legacy deployments, Open Identity Platform Community link:https://github.com/OpenIdentityPlatform/.github/wiki/Approved-Vendor-List[Approved Vendors, window=\_blank] can assist you in the migration process.

[#upgrade-legacy]
.To Migrate a Legacy Deployment
====

. Back up the existing deployment. Inventory realms, authentication modules and chains, policies, OAuth 2.0 and OpenID Connect clients, agent profiles, and federation metadata and partners. Record the keystores, key aliases, trust settings, identity data, and any custom code or configuration each integration uses.

. Install the target release in a separate deployment as described in xref:../install-guide/chap-install-core.adoc[Installing OpenAM Core Services]. Give it separate endpoints, configuration and session stores, and cookie settings that prevent interference with the existing deployment. Plan how to migrate identity data or connect to a compatible data store without affecting the legacy deployment during testing.

. Recreate the settings and integrations you need using the target release's configuration tools. For individual objects, import only data whose format and semantics you have verified against the target release. Leave the new service configuration intact and apply the required settings individually. Review URL changes with application owners and federation partners, and migrate the keys and trust material required by the integrations you retain.

. Before switching traffic, test sign-in, logout, policy decisions, agent connectivity, and the OAuth 2.0, OpenID Connect, and federation flows you use. Verify the behavior of existing sessions and tokens during the transition and plan for users to sign in again if needed.

. Switch client application traffic during a planned cutover and monitor the new deployment. Keep the legacy deployment and its routing configuration available until the rollback window closes. Plan how to reconcile changes made during cutover if you need to route traffic back to the legacy deployment.
