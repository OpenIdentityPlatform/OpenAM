[#chap-about-upgrades]
== About Upgrading OpenAM

This chapter covers common aspects of upgrading an OpenAM deployment, whether you are moving to a new maintenance release, upgrading to a new major release, or migrating from a legacy release to a newer OpenAM release.

Release levels, and how much change to expect in a maintenance, minor, or major release, are defined in xref:../admin-guide/appendix-interface-stability.adoc#release-levels["Product Release Levels"] in the __Administration Guide__. Release levels are identified by version number.

[#sec-supported-upgrades]
=== Upgrade Paths

Use the exact source and target release and the configuration store type to select a path. Rehearse each upgrade on a copy of your deployment with the same directory versions, topology, and customizations.

[#am-supported-upgrades]
.Direct upgrades to OpenAM 16.1.4
[cols="1,1,2,2",options="header"]
|===
|Source |Target |Embedded OpenDJ configuration store |External configuration store
|16.1.3 |16.1.4 |Verified, OpenDJ 5.1.2 to 5.2.0 |Verified with external OpenDJ 5.2.0
|15.2.2 |16.1.4 |Verified, OpenDJ 4.10.2 to 5.2.0 |Verified with external OpenDJ 5.2.0
|===

Verification covers a single OpenAM node with the WAR on JDK 21 and Tomcat 11.0.29 for the target release. The 15.2.2 tests used Tomcat 9.0.124 for the source release. The checks cover the upgrade report, the version after restart, administrator and user sign-in, and preservation of test configuration and profile data. The embedded 15.2.2 test also verified rollback to the previous WAR, container, and offline snapshot. Rehearse your own topology before upgrading production.

For other version pairs, confirm the path for your topology before using the xref:chap-upgrade-servers.adoc#upgrade-server[server upgrade procedure]. See the https://github.com/OpenIdentityPlatform/OpenAM/security/policy#supported-versions[project support policy] for maintained release families and support options. See xref:chap-legacy-servers.adoc#upgrade-legacy[the legacy migration guidance] for older releases.

[#upgrade-planning]
=== Planning the Upgrade

Read the release notes for the target and all intervening releases. Review the xref:../release-notes/requirements-and-upgrade.adoc[platform requirements and compatibility changes] and the xref:chap-upgrade-servers.adoc#upgrade-released-changes[server upgrade notes] with your application owners. Test maintenance releases as well as major and minor releases. Check the versions of your policy agents and administration tools as part of the rehearsal.

Run the Upgrade Wizard or the command-line upgrade tool to update OpenAM's configuration to the target version. Both methods follow the same xref:chap-upgrade-servers.adoc#upgrade-server[server upgrade procedure] for deployment, migration, restart, and validation.

[#pre-upgrade-runtime]
==== Check Java and the Web Container

OpenAM 16.1.4 requires Java 11 or later and a Jakarta EE web container. Tomcat 10.1 requires Java 11 or later. Tomcat 11 requires Java 17 or later, and the 16.1.4 Docker image pairs it with JRE 25. Use a version supported by both OpenAM and the container. Review the xref:../install-guide/chap-prepare-install.adoc#prepare-java[JVM settings] and xref:../install-guide/chap-prepare-install.adoc#prepare-apache-tomcat[Tomcat prerequisites].

When moving from a Java EE deployment, rebuild servlet-dependent custom code against the target release and migrate `javax.servlet` imports and descriptors to Jakarta APIs. Review JSPs, libraries, filters, listeners, and any customization of `web.xml`. A WAR built for Jakarta EE requires a Jakarta container such as Tomcat 10.1 or 11.

[#pre-upgrade-external-stores]
==== Check External Directory Stores

Record the endpoints, base DNs, bind identities, certificate trust, schema, indexes, and replication arrangement of each external store. From the target runtime, check connectivity and TLS to each configured directory server, including failover servers.

* *Configuration store*. Confirm that the target OpenAM release supports your LDAP server. Check that the bind identity can read and update OpenAM's configuration and has the privileges required for the operations performed by the upgrade. Coordinate any separate schema and index changes with the directory administrator. See xref:../install-guide/chap-prepare-install.adoc#prepare-configuration-store[Preparing an External Configuration Data Store].
* *Identity stores*. Check authentication and user and group searches in each realm. Confirm schema and permissions for the writes the deployment uses, such as password changes, account lockout, or profile updates. See xref:../install-guide/chap-prepare-install.adoc#prepare-identity-repository[Preparing an External Identity Repository].
* *Core Token Service (CTS)*. Check the directory version, credentials, schema, and indexes used for session and token operations. Verify replication and the expected failover behavior when you use multiple directory servers. See xref:../install-guide/chap-cts.adoc[Configuring the Core Token Service].

[#upgrade-policies]
=== Legacy Policy Migrations

When a migration path crosses the policy format change introduced after OpenAM 11.0.x, the upgrade process changes how OpenAM represents policies. Most earlier policies transform directly to the newer representation.

If however the upgrade process encounters problems during the transformation, it writes messages about the problems in the upgrade log. When you open a policy in the policy editor that caused problems during the upgrade process, the policy editor shows the issues, but does not let you fix them directly. Instead you must create equivalent, corrected policies in order to use them in OpenAM.

You should therefore plan to test policy upgrade before upgrading the service, and to correct any problems encountered before using the upgraded service.

For details on how to configure OpenAM policies, see xref:../admin-guide/chap-authz-policy.adoc["Defining Authorization Policies"] in the __Administration Guide__.


[#upgrade-authentication-defaults]
=== Authentication Settings and Tools

OpenAM 16.1.4 disables module-based authentication and enables account lockout with a 30-minute duration on new installations. An upgraded installation retains the authentication settings of each realm.

Review the callers in each realm before adopting these defaults. Disabling module-based authentication prevents the following uses.

* Login by module, using the `module=__module-name__` login parameter, or `authIndexType=module` in the REST API.

* Login by authentication level, using the `authlevel=__level__` login parameter, or `authIndexType=level` in the REST API.

* Policies whose environment conditions include *Authentication Level* or *Authentication Scheme*. The re-authentication such a condition asks for reaches OpenAM as module-typed composite advice, which is refused along with the rest of module-based authentication, so the user is denied access instead of being sent to authenticate. Express policy step-up with the *Authenticate to Realm* or *Authenticate to Service* conditions instead, which are unaffected.

The `Application` module and modules of type `Federation` are exempt from the switch, so policy agent authentication and federation flows continue to work. A federation deployment whose SAML v2 Authentication Context mapping names an ordinary module — an entry of the form `module=__module-name__` in the IdP extended metadata — is an exception: that login is made by module and is refused like any other. Map such a context onto a chain with `service=__chain-name__`, or leave its authentication scheme empty, which is what the shipped mapping does.

If you enabled the legacy Liberty ID-WSF endpoints, check the Authentication Service. Its PLAIN and CRAM-MD5 SASL mechanisms, exposed at `/openam/Liberty/*`, log in through `IndexType.MODULE_INSTANCE` against the top level realm, aimed at the modules named by `PlainMechanismAuthModule` and `CramMD5MechanismAuthModule` (both default to `DataStore`). Disabling module-based authentication in the top level realm therefore refuses every SASL request to that endpoint with `MODULE_BASED_AUTH_NOT_ALLOWED`. Where such an integration exists, keep module-based authentication enabled in the top level realm.

Check the Security Token Service (STS) mappings in each realm. The default authentication target mappings of a REST STS instance validate OpenID Connect ID tokens against the `oidc` module and X.509 certificates against `cert_module` with `authIndexType=module`, and the default X.509 mapping of a SOAP STS instance does the same. In a realm where module-based authentication is disabled, these validations are refused with `MODULE_BASED_AUTH_NOT_ALLOWED`. Keep module-based authentication enabled in the realm of the STS instance, or map the token type onto a chain that contains the module, for example `OPENIDCONNECT|service|oidcChain|oidc_id_token_auth_target_header_key=oidc_id_token`. The SOAP STS agent logs in through the `Application` module and is unaffected.

Set a positive lockout duration when enabling timed account lockout. A duration of `0` selects physical locking, which sets `inetuserstatus=Inactive` after the configured number of failed logins and requires an administrator to reactivate the account.

To apply these settings to a realm, use the following command.

[source, console]
----
$ ssoadm set-realm-svc-attrs \
 --adminid amadmin \
 --password-file pwd.txt \
 --realm / \
 --servicename iPlanetAMAuthService \
 --attributevalues sunEnableModuleBasedAuth=false \
                   iplanet-am-auth-login-failure-lockout-mode=true \
                   iplanet-am-auth-lockout-duration=30
----

The same settings are on the console page Realms > __Realm Name__ > Authentication > Settings, under the Security and Account Lockout tabs. For details of the attributes, see xref:../admin-guide/chap-auth-services.adoc#auth-core-security["Core Authentication Attributes - Security"] and xref:../admin-guide/chap-auth-services.adoc#auth-core-account-lockout["Core Authentication Attributes - Account Lockout"] in the __Administration Guide__.

The 16.1.4 configuration upgrade deactivates active built-in identities that still have their shipped passwords. This covers `demo`, `wsc`, `wsp`, `SecurityTokenService`, and `agentAuth`. Check the upgrade report for the affected identities. For an integration that still requires one of them, set a deployment-specific password, update the integration, and reactivate the identity. Beginning with 16.1.4, OpenAM rejects password-based login for the Top Level Realm's `anonymous` user. The Anonymous authentication module continues to provide anonymous access.

Beginning with 16.1.4, `ssoadm` follows the Administrator Authentication Configuration of the top level realm and falls back to the Organization Authentication Configuration when no administrator chain is set. It supports chains that use only user name and password callbacks. If your `ssoadm` script sets `org.forgerock.openam.ssoadm.auth.indexType` and `org.forgerock.openam.ssoadm.auth.indexName`, an index type of `module_instance` requires module-based authentication in that realm. To use a password-only chain, set the index type to `service` and the index name to that chain. To use the default selection, remove both overrides.

[#upgrade-best-practices]
=== Best Practices for Upgrades

[#plan-upgrade-downtime]
==== Plan Downtime and Restrict Maintenance Access

Take every OpenAM server that reads the same configuration store or its replicas out of service for the upgrade. That scope can span several OpenAM sites. Plan for mixed versions to be offline during configuration migration and until you have upgraded and validated each node. Send client traffic to another deployment only if its configuration is independent and its identity and session dependencies can safely continue serving traffic. Otherwise schedule an outage.

Before the first startup on the target version, use network or proxy access controls to limit the upgrade interface to the administrators and tools performing the work. The Upgrade Wizard can be initiated without an authenticated OpenAM session. Protect the direct node URLs and remove public routes to the upgrade interface, including any load balancer or ingress routes that bypass the maintenance controls. Use HTTPS with a trusted certificate for the management endpoint.

[#pre-upgrade-backup]
==== Back Up the Deployment

Capture a coordinated pre-upgrade recovery point after draining traffic and stopping the affected OpenAM servers. Quiesce writes to the stores being backed up as needed to obtain a consistent snapshot. Include the following in the backup.

* The previous WAR or container image and each node's configuration directory, bootstrap files, keystores and trust stores, encryption material, and local customizations. For a Tomcat WAR deployment, this can include `~/openam/` and `~/.openamcfg/`. For the OpenAM Docker image, back up each volume mounted at `/usr/openam/config`.
* The embedded OpenDJ databases and configuration, or the external configuration directory's data, schema, and replication state. Use the directory server's backup and restore procedures. An LDIF export of the configuration suffix can supplement a full backup. See xref:../admin-guide/chap-backup-restore.adoc[Backing Up and Restoring OpenAM Configurations].
* The data and schema of any identity and CTS stores affected by the upgrade. Coordinate recovery of shared stores with their owners and record which sessions or tokens may be lost during a restore.
* The previous Java runtime and web container, and deployment settings for the container, proxy, or Docker service. Record host names, port and context path mappings, runtime configuration, and secrets. Keep copies of local administration tool changes and policy agent installation and configuration files where they are affected.

Verify that you can restore this recovery point on a test deployment before upgrading production.

[#pre-upgrade-customization]
==== Apply Customization Before Upgrading

Start with the target WAR or image and reapply your customizations, using the target files and dependencies as the base. Test the rebuilt deployment on the target Java and container versions. Review these common customization points.

* Plugins and extensions such as custom authentication modules, response attribute providers, post authentication plugins, SAML v2.0 attribute mappers, and OAuth 2.0 scope implementations
+
These are described in the xref:../dev-guide/index.adoc[Developer's Guide].

* Customized JSPs, redesigned login or service pages, additional CSS and visual content, and modified authentication module callback files
+
These are described in the xref:../install-guide/chap-custom-ui.adoc["Customizing the OpenAM End User Pages"] in the __Installation Guide__.

* Any changes to OpenAM classes

* Any changes or additional Java class libraries (such as .jar files in `WEB-INF/lib`)

[#upgrade-device-flow-form]
Beginning with 16.1.4, the OAuth 2.0 device flow requires a CSRF token on the user code page. Carry the token into your customized copy before upgrading. The endpoint `/oauth2/device/user` refuses any submission without a valid `csrf` parameter with HTTP 400, and the stock page supplies that token through two lines that a customized copy made from an earlier release lacks. Without them, every user code a browser submits is refused.

* In a customized `CodeVerificationForm.ftl` (for example, one placed in `WEB-INF/classes/templates`), add the token to `pageData`:
+
[source, html]
----
<#if csrf??>csrf: "${csrf?js_string}",</#if>
----

* In a customized XUI `templates/user/DeviceTemplate.html`, add a hidden field inside the form:
+
[source, html]
----
<input type="hidden" name="csrf" value="{{csrf}}">
----

Carry over the stock form's RequireJS `urlArgs` setting to refresh any cached `DeviceTemplate.html` in the browser. Also keep its submit listener, which injects the CSRF token if the field is missing.

Clients that post the user code directly, without the page, send their session ID as the `csrf` parameter. For details, see xref:../dev-guide/chap-client-dev.adoc#proc-device-flow-allow-access["To Grant Consent in the OAuth 2.0 Device Flow"] in the __Developer's Guide__.

[#upgrade-device-flow-verification-uri-query]
In 16.1.4, a link or QR code that opens the device verification page with the user code in the query string, such as `/oauth2/device/user?user_code=BDCT-HQKD`, now redirects (HTTP 303) to the same address without that parameter. The user types the code into the empty form the redirect leads to. Update custom device apps and QR codes to present the verification URI and the user code separately.

[#upgrade-consent-decision-body]
Beginning with 16.1.4, `/oauth2/authorize` and `/oauth2/device/user` read `decision` and `save_consent` from the POST body. Update custom clients that use the query string. A missing body decision denies authorization at `/oauth2/authorize`. At `/oauth2/device/user` it submits the user code form and leads to the consent page, or approves the device code when the client's consent is implied.

[#post-upgrade-rollback]
==== Plan for Rollback

If validation fails, keep traffic drained and stop all nodes in the affected configuration scope. Restore the pre-upgrade WAR and runtime, or the previous image. Restore the matching per-node files and directory stores from the same recovery point. Coordinate the restoration of replicated stores so that a peer with newer data cannot overwrite the restored state. Recover affected identity and CTS data according to the recovery plan. Restart the old deployment only after the stores and local files are ready, then repeat the functional checks before restoring traffic.

For web policy agents, restore the old installation and configuration, including any changed centrally stored agent configuration. For Java policy agents, reinstall the earlier agent and restore its configuration.
