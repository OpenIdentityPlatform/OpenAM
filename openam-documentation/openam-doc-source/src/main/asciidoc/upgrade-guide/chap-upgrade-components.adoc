[#upgrade-web-policy-agents]
.Upgrading Web Policy Agents
====

. Verify that the selected agent version is compatible with the target OpenAM release, web server version, operating system, and architecture. If both OpenAM releases will serve traffic during the upgrade, verify every agent and server combination that will handle requests. See the https://github.com/OpenIdentityPlatform/OpenAM-Web-Agents/releases[web policy agent releases] and https://github.com/OpenIdentityPlatform/OpenAM-Web-Agents[agent project documentation].

. Back up the agent installation, local agent configuration, web server configuration, and any agent profile or group settings stored in OpenAM.

. Stage the new agent on a test web server. Follow the selected release's upgrade procedure if it covers the existing installation. Otherwise, install the new agent and reapply compatible settings.

. Test sign-in, policy decisions for allowed and denied requests, logout, and session or policy notifications where configured.

. Take each web server instance out of rotation before updating its agent. Verify the instance with the target OpenAM deployment before returning it to service.

====

[#upgrade-java-ee-policy-agents]
.Upgrading Java Policy Agents
====

. Verify that the selected agent version is compatible with the target OpenAM release and the protected application's Java runtime, container version, and servlet API (`javax.servlet` or `jakarta.servlet`). If both OpenAM releases will serve traffic during the upgrade, verify every agent and server combination that will handle requests. See the https://github.com/OpenIdentityPlatform/OpenAM-JEE-Agents/releases[Java policy agent releases] and https://github.com/OpenIdentityPlatform/OpenAM-JEE-Agents[agent project documentation].

. Back up the agent installation, local agent configuration, affected application and container configuration, and any agent profile or group settings stored in OpenAM.

. Stage the new agent in a test container. Follow the selected release's upgrade procedure if it covers the existing installation. Otherwise, install the new agent and reapply compatible settings, including the agent filter configuration for each protected application.

. Test sign-in, policy decisions for allowed and denied requests, logout, and notifications where configured.

. Redirect client traffic before updating each production container. Verify the protected applications with the target OpenAM deployment before restoring traffic.

====

[#upgrade-tools]
.Upgrading OpenAM Tools
====

. Install and configure the xref:../install-guide/chap-install-tools.adoc[OpenAM tools] from the target server release in a separate directory.

. Reapply the environment settings, script customizations, and site URL mapping that your deployment needs. Configure the tools' Java truststore to trust the certificates used by the OpenAM endpoints and any LDAPS connections required by the tools.

. Run a read-only authenticated command with the new `ssoadm`, such as `ssoadm list-servers -u amadmin -f /path/to/password-file`, and confirm that it lists the expected servers. Verify the scripts and automation that use the tools before switching to the new installation.

====

[#upgrade-elliptic-curve-algorithms]
.Adopting ECDSA for Stateless Sessions and OpenID Connect
====

Use this procedure if you plan to switch to signing with the Elliptic Curve Digital Signature Algorithm (ECDSA). Verify consumer support and back up the current keystores and configuration. Preserve keys and aliases that other integrations still use. Test how the change affects outstanding sessions and tokens, and plan for reauthentication or token reissuance if needed.

. Create a key pair for each algorithm you plan to use (`ES256` with P-256, `ES384` with P-384, or `ES512` with P-521). Use the key generation procedure in xref:../admin-guide/chap-session-state.adoc#session-state-configure-ecdsa-signing[Configuring Elliptic Curve Digital Signature Algorithms]. On each OpenAM server that issues or verifies the sessions or tokens, configure the same key pairs under the same aliases.

. To change stateless session signing, follow the session configuration steps in that procedure. Test newly issued sessions across the site's servers.

. To change OpenID Connect ID token signing, configure the provider and client in their realm.
+
.. Under Services > OAuth2 Provider, add the algorithms you plan to offer to *ID Token Signing Algorithms supported*. In *Token Signing ECDSA public/private key pair alias*, map each algorithm to a key alias using the `algorithm|alias` format, such as `ES256|es256-signing`. The alias must refer to a key pair in the keystore configured by `com.sun.identity.saml.xmlsig.keystore`. Save the provider settings.
+
The provider's *OAuth2 Token Signing Algorithm* setting controls stateless OAuth 2.0 token signing. Change it only if you also plan to change how those tokens are signed.

.. Under Agents > OAuth 2.0/OpenID Connect Client, select the client profile and set *ID Token Signing Algorithm* to the chosen ECDSA algorithm. Save the profile.

.. Check that the realm's OpenID Connect discovery document advertises the algorithm and that its `jwks_uri` exposes the expected public key. Verify that the client can validate a newly issued ID token. See xref:../admin-guide/chap-oauth2.adoc#configure-digital-signing[To Configure Digital Signatures].

====

[#upgrade-user-services]
.Migrating a User Self-Service Keystore
====

[#self-services_upgrade]
Use these steps if you are migrating a legacy keystore for REST-based user self-service. User self-service uses a JCEKS keystore with a key pair for encryption and a secret key for signing. Where the service already works with a suitable keystore, preserve its keys and aliases during the upgrade.

. Back up the existing keystore and settings. Prepare a JCEKS keystore containing the required production keys. Preserve the other keys, certificates, and aliases used by the deployment before switching a shared keystore. Account for pending self-service links if the keys must change.

. Under Configure > Server Defaults > Security > Key Store, set *Keystore File* to the prepared file and *Keystore Type* to `JCEKS`. Update any overrides under Deployment > Servers > _Server Name_ > Security > Key Store. Configure the same signing and encryption keys under the same aliases on every OpenAM server handling self-service requests for the deployment.

. Restart each affected server and configure the *Encryption Key Pair Alias* and *Signing Secret Key Alias* as described in xref:../admin-guide/chap-usr-selfservices.adoc#configuring-self-service-keys[To Configure Self Service Key Aliases].

. Before restoring traffic, test the self-service flows you use. In a load-balanced site, verify that a flow started on one server can complete on another.
