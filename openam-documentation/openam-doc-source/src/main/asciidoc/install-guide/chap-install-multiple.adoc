== Installation Considerations for Multiple Servers

ifdef::env-site[]
anchor:chap-install-multiple[]
endif::[]

[#considerations-multiple-servers]
=== Things to Consider When Installing Multiple Servers

An OpenAM site groups one or more OpenAM servers behind a load balancer. The load balancer sends requests to healthy nodes and can also terminate HTTPS and restrict which endpoints are public.

Use distinct hostnames such as `am1.internal.example.com` and `am2.internal.example.com` for the OpenAM nodes. Configure the site's Primary URL as the public entry point, such as `https://lb.example.com/openam`. The cookie domain is a DNS name, such as `lb.example.com` or a shared domain such as `example.com` when an application also needs the cookie. Configure the cookie domain to match the public hostname and the scope needed by the deployment. See xref:../reference/chap-config-ref.adoc#system-platform-attrs[Platform].

Keep the administrative console and internal endpoints on private listeners where the deployment allows it. See xref:../how-to/how-to-restrict-xui-access-with-a-reverse-proxy.adoc#how-to-restrict-xui-access-with-a-reverse-proxy[Restrict XUI Access with a Reverse Proxy].

[#configure-sites]
=== Configuring OpenAM Sites

The most expedient way to configure a server in a site is to set the site up during the initial OpenAM configuration. In the GUI configurator, this is done in the Site Configuration screen.

You can also configure a site after installation.

[#configure-site-after-installation]
.To Configure a Site With a First OpenAM Server
====
The following steps show how to set up the site for the first OpenAM server.

. Sign in to the OpenAM console as an administrator and go to Deployment > Sites.

. Click New to start configuring the new site.

. On the New Site page enter the site name, and set the Primary URL to the load balancer URL that is the entry point for the site, such as `\https://lb.example.com/openam`.
+
The site URL is the URL to the load balancer in front of the OpenAM servers in the site. For example, if your load balancer listens for HTTPS on host `lb.example.com` and port `443` with OpenAM under `/openam`, then your site URL is `\https://lb.example.com/openam`.
+
Client applications and policy agents access the servers in the site through the site URL.

. Click Save to keep the site configuration.

. Navigate to Deployment > Servers > __Server Name__ > General.

. Set the Parent Site to the name of the site you just created, and then select Save Changes.
+
At this point, the server is part of the new site you have configured.
+
For all additional servers in the OpenAM site, add them to the site at configuration time as described in xref:chap-install-core.adoc#add-servers-to-site["To Add a Server to a Site"].

====


[#configure-lb]
=== Configuring Load Balancing for a Site

Plan load balancing for multi-request authentication and for requests using an established session. A sign-in exchange can retain node-local state even when the realm issues stateless sessions. See xref:../admin-guide/chap-session-state.adoc#chap-session-state[Configuring Session State] and xref:chap-session-failover.adoc#chap-session-failover[Setting Up OpenAM Session Failover].

[#configure-lb-stateful]
==== Load Balancer Configuration for Stateful Sessions

A serving node can retrieve an established stateful session from CTS. Cookie affinity can improve performance by directing subsequent requests to a node that has the session cached. The default cookie name is `amlbcookie`.

[#configure-site-load-balancing]
.To Configure Site Load Balancing for Deployments With Stateful Sessions
====

. For each OpenAM server in the site, navigate to Deployment > Servers > __Server Name__ > General, set Parent Site to the site you created, and save.
. If you use `amlbcookie` affinity, verify that the cookie value is unique for each server. The default is the server ID. Review `com.iplanet.am.lbcookie.value` in the server's Advanced settings. Verify any requirements of integrations using the server ID before changing the value. Restart each server whose value changed.
. Configure the load balancer to map each cookie value to the corresponding server. Route requests with a missing or unknown value, or a value for an unavailable server, to a healthy node.
. Verify that each node can reach the CTS store. Test requests without the affinity cookie and confirm that an established stateful session can resume after removing a node from service. See xref:chap-session-failover.adoc#chap-session-failover[Setting Up OpenAM Session Failover].

====

[#lb-termination]
===== Load Balancer Termination

A load balancer or proxy needs to terminate TLS to read HTTP cookies. Use TLS to the backend and verify its certificate and hostname. If the first hop passes TLS through, apply the cookie affinity at the next hop that terminates TLS.

Configure the proxy and servlet container to represent the public HTTPS scheme, host, port, and context path to OpenAM. Verify the resulting URL and redirects from the public endpoint. See xref:../admin-guide/chap-openid-connect.adoc#configure-base-url-source[Configuring the Base URL Source Service].

[#lb-and-crosstalk]
===== Affinity and Authentication Requests

REST clients that send the session token in a request header may omit `amlbcookie`. The load balancer can send these requests, and retries following a node failure, to any healthy node. The receiving OpenAM server can load a stateful session from the shared CTS. Test how queued writes and replication lag affect request routing and session recovery. See xref:chap-session-failover.adoc#test-openam-session-failover[To Test OpenAM Session Failover].

Before a session is established, test how the load balancer keeps requests in a multi-step authentication flow on the same node, including REST clients that do not retain cookies. Test how the client restarts the flow if that node becomes unavailable.

[#configure-lb-stateless]
==== Load Balancer Configuration for Stateless Sessions

Authenticated requests with stateless sessions can go to any healthy OpenAM server with the site's shared configuration and keys. The server validates the state in the client token. If you enable stateless session blacklisting, all nodes need access to the same CTS data. Plan affinity separately for authentication exchanges that keep state on one node.

[#handle-request-headers]
=== Handling HTTP Request Headers

OpenAM authentication can use the client IP address for decisions such as adaptive authentication. If a proxy supplies the address in `X-Forwarded-For`, configure the trusted proxy to replace the incoming header with the verified client IP address. Restrict backend network access to trusted proxies and management hosts. Block direct public access to the backend.

Set `com.sun.identity.authentication.client.ipAddressHeader` to `X-Forwarded-For` under Deployment > Servers > __Server Name__ > Advanced on each OpenAM server that receives the header. Verify through the public URL that OpenAM receives the intended address even when the client sends its own header. See xref:../how-to/how-to-restrict-xui-access-with-a-reverse-proxy.adoc#how-to-restrict-xui-access-with-a-reverse-proxy[Restrict XUI Access with a Reverse Proxy].

[#handle-multiple-cookie-domains-wildfly]
=== Handling Multiple Cookie Domains When Using Wildfly

If you are using Wildfly as the OpenAM web container with multiple cookie domains, you must set the advanced server property, `com.sun.identity.authentication.setCookieToAllDomains`, to `false`.

Set this property in the OpenAM console under Configure > Server Defaults > Advanced.
