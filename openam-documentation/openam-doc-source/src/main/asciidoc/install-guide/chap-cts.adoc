== Configuring the Core Token Service

ifdef::env-site[]
anchor:chap-cts[]
endif::[]

The Core Token Service (CTS) stores OpenAM tokens in LDAP. OpenAM uses CTS for stateful sessions and for tokens used by services such as OAuth 2.0, SAML 2.0, and UMA. CTS also holds logout records when you enable stateless session blacklisting. See xref:../admin-guide/chap-session-state.adoc[Configuring Session State].

[#cts-general-recommend]
=== General Recommendations for CTS Configuration

* The default configuration stores CTS data in the configuration directory. Use the embedded directory for evaluation and small single-server deployments. A dedicated external directory lets you size and tune CTS independently of the configuration and identity stores.
* Size and monitor the directory for the deployment's write rate, token volume, and replication load. See xref:../deployment-planning/chap-sizing.adoc#size-for-service-levels[Sizing For Service Levels] and xref:#cts-tuning-considerations[CTS Tuning Considerations].
* *Choose a CTS connection strategy*. With an external OpenDJ CTS store, choose between two connection strategies.
+
** *Active/passive*. Each OpenAM server uses the first available replica in its pool. It prioritizes replicas assigned to that server, then those assigned to its site, then the remaining replicas. Servers at different sites can therefore use different preferred replicas.
** *Affinity*. Within a pool, OpenAM maps the hash of a token DN to a position in the ordered replica list. Requests for that DN start with the same replica, and the pool tries another replica if the first is unavailable.
+
Affinity across pools requires the same replicas in the same effective order. OpenAM shuffles replicas of equal priority when it builds each pool, so identical connection strings can produce different orders. If your deployment relies on cross-node affinity, verify that the same test DN selects the same initial replica on each node with the replicas available. Repeat after the pools are reinitialized.
+
List the directory servers directly in Connection String(s). An external LDAP load balancer hides the individual replicas from OpenAM.
A read can reach a different replica before the corresponding write arrives, including during failover or a change in the preferred site.
Test response times, replication lag, and recovery for the selected strategy.

* For service across data centers, use the same replicated CTS data across sites. An upstream traffic manager must route clients to a healthy site and preserve the public URL and cookie scope needed by the client. Measure how long new and revoked sessions take to converge under realistic load. See xref:chap-session-failover.adoc#chap-session-failover[Setting Up OpenAM Session Failover].

The diagram shows two OpenAM servers behind one load balancer. Both use a separate pair of directory servers for configuration and a pair of replicas for CTS. In the CTS pair, both OpenAM servers prefer the same primary and can connect directly to the other replica.

[#cts-deployment-steps]
=== CTS Deployment Steps

These steps use OpenDJ 5.2.0 and two OpenAM nodes in one site. The directory replicas are `cts1.example.com` and `cts2.example.com`. Both have an LDAPS listener on port 1636, an administration connector on port 4444, and a dedicated backend named `userRoot` with the base entry `dc=cts,dc=example,dc=com`. See xref:chap-install-multiple.adoc#configure-site-load-balancing[To Configure Site Load Balancing for Deployments With Stateful Sessions].

[#cts-opendj-preparation]
==== Prepare the OpenDJ Directory Service for CTS

[#cts-download-opendj]
.To Download and Install OpenDJ
====

. Download and unpack link:https://github.com/OpenIdentityPlatform/OpenDJ/releases/tag/5.2.0[OpenDJ 5.2.0]. Run `./setup --cli` from each OpenDJ installation directory. Create the base entry for `dc=cts,dc=example,dc=com` in the `userRoot` backend and enable LDAPS. See link:https://doc.openidentityplatform.org/opendj/install-guide/chap-install#command-line-install[Installing OpenDJ From the Command Line].
. Configure a certificate valid for each replica's DNS name. Add the issuing CA to the truststore used by OpenDJ client tools, and configure the OpenAM JVM on each node to trust the same CA. Limit LDAP and administration ports to the hosts that need them.
. From the OpenDJ installation directory, set the variables below for the first replica. Use an existing password file readable only by the operator and a truststore that verifies the replica's certificate. If the truststore requires a password, pass `--trustStorePasswordFile` with the path to its protected password file to each client command.
+
[source,bash]
----
DJ_HOST=cts1.example.com
DJ_ADMIN_PASSWORD_FILE=/secure/path/dj-admin-password
DJ_TRUSTSTORE=/secure/path/dj-truststore.jks
CTS_TEMPLATES=/path/to/tomcat/webapps/openam/WEB-INF/template/ldif/sfha
CTS_BASE_DN='dc=cts,dc=example,dc=com'
CTS_ROOT_DN="ou=famrecords,ou=openam-session,ou=tokens,$CTS_BASE_DN"
CTS_BACKEND=userRoot
CTS_WORK_DIR=$(mktemp -d)
----

====

[#cts-import-schema]
==== Import CTS Files

Use the templates from the OpenAM WAR you deploy. These procedures assume a new CTS backend. Follow the product upgrade instructions for an existing store.

[#cts-import-config]
.To Import the CTS Configuration
====

. Install the CTS schema and multivalue schema on each replica before first use. Run the following commands for each host by setting `DJ_HOST` to that host.
+
[source,bash]
----
./bin/ldapmodify --hostname "$DJ_HOST" --port 1636 --useSSL \
  --trustStorePath "$DJ_TRUSTSTORE" \
  --bindDN 'cn=Directory Manager' --bindPasswordFile "$DJ_ADMIN_PASSWORD_FILE" \
  "$CTS_TEMPLATES/cts-add-schema.ldif" "$CTS_TEMPLATES/cts-add-multivalue.ldif"
----

. On the first replica, create the token containers. The deepest container is the root DN that OpenAM will use for CTS.
+
[source,bash]
----
DJ_HOST=cts1.example.com
sed "s/@SM_CONFIG_ROOT_SUFFIX@/$CTS_BASE_DN/g" \
  "$CTS_TEMPLATES/cts-container.ldif" > "$CTS_WORK_DIR/cts-container.ldif"
./bin/ldapmodify --hostname "$DJ_HOST" --port 1636 --useSSL \
  --trustStorePath "$DJ_TRUSTSTORE" \
  --bindDN 'cn=Directory Manager' --bindPasswordFile "$DJ_ADMIN_PASSWORD_FILE" \
  "$CTS_WORK_DIR/cts-container.ldif"
----

====

[#cts-nonadmin-creation]
==== Non-Admin User Creation and ACI Import

Provision a regular LDAP service account for OpenAM. Use Directory Manager for the installation commands only.

[#ct-non-admin-user]
.To Create a Non-Admin User
====

. Save the following entries as `cts-access.ldif` in `$CTS_WORK_DIR`. Replace the placeholder with a generated service password and keep the file readable only by the operator. Use LDIF base64 syntax if required for the password value.
+
[source,ldif]
----
dn: ou=admins,dc=cts,dc=example,dc=com
objectClass: top
objectClass: organizationalUnit
ou: admins

dn: uid=openam_cts,ou=admins,dc=cts,dc=example,dc=com
objectClass: top
objectClass: inetOrgPerson
uid: openam_cts
cn: OpenAM CTS
sn: CTS
userPassword: REPLACE_WITH_SERVICE_PASSWORD
ds-rlim-size-limit: 5000
ds-rlim-lookthrough-limit: 0

dn: ou=famrecords,ou=openam-session,ou=tokens,dc=cts,dc=example,dc=com
changetype: modify
add: aci
aci: (targetattr="*")(version 3.0; acl "OpenAM CTS token attributes";
 allow (read,search,compare,write)
 userdn="ldap:///uid=openam_cts,ou=admins,dc=cts,dc=example,dc=com";)
aci: (version 3.0; acl "OpenAM CTS token entries"; allow (add,delete)
 userdn="ldap:///uid=openam_cts,ou=admins,dc=cts,dc=example,dc=com";)
aci: (targetcontrol="2.16.840.1.113730.3.4.3")
 (version 3.0; acl "OpenAM CTS persistent search"; allow (read)
 userdn="ldap:///uid=openam_cts,ou=admins,dc=cts,dc=example,dc=com";)
----

. Import the account and the access controls into the first replica.
+
[source,bash]
----
./bin/ldapmodify --hostname "$DJ_HOST" --port 1636 --useSSL \
  --trustStorePath "$DJ_TRUSTSTORE" \
  --bindDN 'cn=Directory Manager' --bindPasswordFile "$DJ_ADMIN_PASSWORD_FILE" \
  "$CTS_WORK_DIR/cts-access.ldif"
----

. Verify that the service account can bind and read the token container. Use a protected file containing the service account password.
+
[source,bash]
----
CTS_BIND_DN="uid=openam_cts,ou=admins,$CTS_BASE_DN"
CTS_PASSWORD_FILE=/secure/path/cts-service-password
./bin/ldapsearch --hostname "$DJ_HOST" --port 1636 --useSSL \
  --trustStorePath "$DJ_TRUSTSTORE" \
  --bindDN "$CTS_BIND_DN" --bindPasswordFile "$CTS_PASSWORD_FILE" \
  --baseDN "$CTS_ROOT_DN" --searchScope base '(objectClass=*)' ou
----
+
The search returns the entry with `ou: famrecords`. Remove the temporary LDIF file containing the password after provisioning.
+
The CTS reaper requests pages of 1000 entries. Set the account's size limit above 1000 so OpenDJ honors the paged results control. The example disables the lookthrough limit for this account on the dedicated CTS directory so the reaper can evaluate large sets of candidates. If you set a finite limit, size it for peak token volume and validate it under load. See link:https://doc.openidentityplatform.org/opendj/admin-guide/chap-resource-limits[Setting Resource Limits].

====

[#cts-index-import-rebuild]
==== CTS Index Import and Build

[#cts-index-setup]
.To Import and Rebuild the CTS Indexes
====

. Import the index templates on each replica. Set `DJ_HOST` to the target and run the commands from that replica's OpenDJ installation directory.
+
[source,bash]
----
for template in cts-indices.ldif cts-add-multivalue-indices.ldif; do
  sed "s/@DB_NAME@/$CTS_BACKEND/g" "$CTS_TEMPLATES/$template" > "$CTS_WORK_DIR/$template"
done
./bin/ldapmodify --hostname "$DJ_HOST" --port 1636 --useSSL \
  --trustStorePath "$DJ_TRUSTSTORE" \
  --bindDN 'cn=Directory Manager' --bindPasswordFile "$DJ_ADMIN_PASSWORD_FILE" \
  "$CTS_WORK_DIR/cts-indices.ldif" "$CTS_WORK_DIR/cts-add-multivalue-indices.ldif"
----

. Rebuild and verify the indexes before making the replica available to OpenAM. Run these commands on the replica while it is stopped.
+
[source,bash]
----
./bin/stop-ds &&
  ./bin/rebuild-index --offline --baseDN "$CTS_BASE_DN" --rebuildAll &&
  ./bin/verify-index --baseDN "$CTS_BASE_DN" --countErrors &&
  ./bin/start-ds
----

. Enable secure replication for `dc=cts,dc=example,dc=com` and initialize the second replica from the first, which holds the CTS containers, the service account, and the ACIs. Check replication status and repeat the service-account search against the second replica. See link:https://doc.openidentityplatform.org/opendj/admin-guide/chap-replication[Managing Data Replication].

[#cts-openam-config]
==== OpenAM CTS Configuration

When switching a running deployment to a different CTS store, schedule a coordinated cutover. Existing CTS records remain in the source store when you change the store settings. With an empty destination, users with existing stateful sessions must sign in again, and clients that use CTS-backed tokens may need new tokens.

Decide which session, token, and revocation records each enabled service needs after the switch. Plan for reauthentication and token reissue where disruption is acceptable. If you need to preserve records, rehearse the transfer and populate the destination store before restarting OpenAM. Account for changes to these records up to the cutover.

If existing sessions must remain usable, establish a test stateful session before the switch and keep the same client session for validation. Allow for idle and maximum session timeouts so the session is still valid when you test it.

Drain all participating OpenAM servers from production traffic before changing these settings and keep administrative access available.

[#cts-openam-gui]
.To Configure CTS in OpenAM
====

. In the OpenAM console, go to Configure > Server Defaults > CTS.
. Under CTS Token Store, set the following values.
+
[#cts-store-settings]
.CTS Token Store Parameters
[cols="1,2"]
|===
|Parameter |Value

|Store Mode
|`External Token Store`

|Root Suffix
|`ou=famrecords,ou=openam-session,ou=tokens,dc=cts,dc=example,dc=com`

|Max Connections
|Keep the default initially and tune under load.
|===

. Under External Store Configuration, set the following values.
+
[#cts-external-store-settings]
.External Store Configuration Parameters
[cols="1,2"]
|===
|Parameter |Value

|SSL/TLS Enabled
|Enabled

|Connection String(s)
|`cts1.example.com:1636,cts2.example.com:1636`

|Login Id
|`uid=openam_cts,ou=admins,dc=cts,dc=example,dc=com`

|Password
|The service account password

|Heartbeat
|`10` seconds

|Affinity Enabled
|Disabled for this primary/failover example
|===

. For OpenAM 16.1.4, set `org.forgerock.openam.ldap.secure.protocol.version` to `TLS` in the Advanced properties of each OpenAM node. The `TLS` setting uses the protocols enabled by the JVM. Make sure the LDAPS listener on each CTS replica supports one of those protocols.
. Save the changes and check for per-server overrides. Restart all participating OpenAM servers to initialize their CTS connection pools with the saved settings. Check their logs for LDAPS connection or bind errors.
+
anchor:cts-global-attribute-settings[]
Stateful sessions use CTS for persistence. Verify a test user's realm uses stateful sessions before testing. Follow xref:chap-session-failover.adoc#enable-session-failover[To Set Up Session Failover After Installation] to verify the site and session settings.
. Sign in as a test user through a restarted node. In a multi-node site, use the load-balanced site URL and direct this sign-in to a specific node. Verify that the new stateful session record was written to external CTS.
. In a multi-node site, stop the issuing node. Use the same site URL and client session to verify that a second restarted node reads the record from external CTS and resumes the session. Bring the issuing node back online after the check.
. If existing sessions must remain usable, use the test session established before the switch to make a request that requires authentication through the same URL. Verify that the request succeeds without signing in again.
. Restore production traffic after the applicable checks pass.

[#cts-testing-failover]
==== Testing Failover

[#cts-test-failover]
.To Test Failover
====

. First, test an OpenAM node failure while both CTS replicas are healthy. Keep the same HTTPS site URL and browser session. See xref:chap-session-failover.adoc#test-openam-session-failover[To Test OpenAM Session Failover].
. Restore both OpenAM nodes before testing a directory replica failure independently. With the primary CTS replica offline, confirm from OpenDJ access logs or OpenAM connection diagnostics that OpenAM uses the remaining replica. Test an existing session on a node that must read it from CTS. Also sign in with a new test session and verify that writes reach the remaining replica.
. Check logout and expiration during failover. Record the time until both OpenAM nodes reject the original test session, including after the failed replica rejoins. Compare observed availability and revocation delay to your deployment's requirements. Account for replication lag, queued writes, and cached session state.
. Restore the primary, check that replication catches up, and repeat the checks with the other replica unavailable.

[#cts-backup-repl-purge-delay]
=== CTS Backups and OpenDJ Replication Purge Delay

OpenDJ retains replication history for the configured `replication-purge-delay`. Align retention with the outage and restore windows you plan to support. A restored replica that is missing changes no longer available in replication history can require reinitialization from a healthy replica. See link:https://doc.openidentityplatform.org/opendj/admin-guide/chap-replication[Managing Data Replication].

Decide whether CTS needs backups and test how to recover safely. Restoring old CTS data can lose recent tokens or revive tokens and sessions revoked after the backup. Include expiration and revocation in your restore checks and plan for reauthentication when recovering from a full loss of CTS.

For example, schedule a daily online backup of the `userRoot` backend at 02:00 in the OpenDJ server's time zone. Run the command with a directory administrator account or a backup operator with the appropriate privilege. On port 4444, the tool connects to the administration connector. Its certificate can have a different issuer from the LDAPS certificate. Set `DJ_TRUSTSTORE` to a truststore that also trusts the administration connector, or use a separate truststore for this command. If the truststore requires a password, supply `--trustStorePasswordFile` with the path to its protected password file. See link:https://doc.openidentityplatform.org/opendj/admin-guide/chap-backup-restore[Backing Up and Restoring Data].

[source,bash]
----
./bin/backup --hostname "$DJ_HOST" --port 4444 \
  --trustStorePath "$DJ_TRUSTSTORE" \
  --bindDN 'cn=Directory Manager' --bindPasswordFile "$DJ_ADMIN_PASSWORD_FILE" \
  --backendID "$CTS_BACKEND" --backupDirectory /path/to/opendj/bak/cts \
  --recurringTask '00 02 * * *'
----

[#cts-recover-expired-token-backlog]
=== Recovering From an Expired Token Backlog

After an interruption, check the OpenAM reaper logs and the OpenDJ access logs for a rejected expiration search. In OpenDJ 5.2.0, a range search on `coreTokenExpirationDate` can exceed the index limit when more than 100,000 tokens have expired. If the directory cannot narrow the search using the search scope, OpenDJ treats it as unindexed. LDAP paging limits the entries returned per page after OpenDJ evaluates the search. Verify the CTS indexes before using the recovery procedure.

Use the following procedure in a maintenance window on a dedicated CTS directory when an expired token backlog causes OpenDJ to reject the reaper's unindexed search.

. On a writable replica, set `DJ_HOST` to that replica and use the LDAPS settings from xref:#cts-opendj-preparation[Prepare the OpenDJ Directory Service for CTS]. Temporarily grant `unindexed-search` to the CTS service account using a directory administrator.
+
[source,bash]
----
CTS_BIND_DN="uid=openam_cts,ou=admins,$CTS_BASE_DN"
./bin/ldapmodify --hostname "$DJ_HOST" --port 1636 --useSSL \
  --trustStorePath "$DJ_TRUSTSTORE" \
  --bindDN 'cn=Directory Manager' --bindPasswordFile "$DJ_ADMIN_PASSWORD_FILE" <<EOF
dn: $CTS_BIND_DN
changetype: modify
add: ds-privilege-name
ds-privilege-name: unindexed-search
EOF
----

. Confirm the account change has replicated. Let the scheduled reaper continue using the CTS account. Check that the searches succeed, the count of expired entries falls, and directory load stays within operating limits.

. Once the backlog has cleared, remove the temporary privilege and confirm the change has replicated.
+
[source,bash]
----
./bin/ldapmodify --hostname "$DJ_HOST" --port 1636 --useSSL \
  --trustStorePath "$DJ_TRUSTSTORE" \
  --bindDN 'cn=Directory Manager' --bindPasswordFile "$DJ_ADMIN_PASSWORD_FILE" <<EOF
dn: $CTS_BIND_DN
changetype: modify
delete: ds-privilege-name
ds-privilege-name: unindexed-search
EOF
----

. Verify that the next scheduled cleanup runs under the regular CTS account and removes newly expired tokens. In a test deployment, rehearse the procedure with an expired token backlog large enough to make the expiration search unindexed. Confirm that unexpired tokens remain available throughout the drill.

[#cts-token-managing]
=== Managing CTS Tokens

Encryption and compression are disabled by default. The CTS worker schedule uses the smaller of the two time settings below.
--

`com.sun.identity.session.repository.enableEncryption`::
Supports encryption of CTS tokens. Default: `false`.

`com.sun.identity.session.repository.enableCompression`::
Enables GZip-based compression of CTS tokens. Default: `false`.

`com.sun.identity.session.repository.enableAttributeCompression`::
Supports compression over and above the GZip-based compression of CTS tokens. Default: `false`.

`com.sun.identity.session.repository.cleanupRunPeriod`::
Contributes to the CTS worker interval, including checks for expired tokens. The default is 300000 ms.

`com.sun.identity.session.repository.healthCheckRunPeriod`::
Also contributes to the CTS worker interval. The default is 60000 ms, which gives a 60-second worker interval with both defaults.

--
To enable the encryption/compression options, navigate to Configure > Server Defaults > Advanced. On the Advanced page, you will see these entries in the `Property Name` column with the corresponding value in the `Property Value` column. To enable them, change `false` to `true` in the Property Value column associated with the desired property, and click Save.

[NOTE]
====
If you want to enable compression or encryption, you must enable the same property on every OpenAM instance within the site, otherwise they will not function correctly together. You must also restart the servers for the changes to take effect.
====

[WARNING]
====
When encryption or compression properties are changed, all previous tokens in the LDAP store will be unreadable; thus, invalidating any user's sessions. As a result, the user will be required to log in again.
====


[#cts-tuning-considerations]
=== CTS Tuning Considerations

The following OpenAM components make CTS requests:

* Session service for stateful session failover

* Session service for stateless session blacklisting

* OAuth 2.0 for token persistence

* SAML v2.0 for token persistence

* UMA for token persistence

* REST API for functions like forgotten passwords

CTS queues directory operations for asynchronous processing. A caller can block while waiting for queue space or for an operation result. Tune the queue properties under realistic load.
--

`org.forgerock.services.cts.async.queue.size`::
Sets the capacity of each CTS task queue. The default is 16000.

`org.forgerock.services.cts.async.queue.timeout`::
Sets the timeout for adding a task to a full queue and for waiting on an asynchronous result. The default is 15 seconds for each wait.

--
To set the queue size and timeout properties, in the OpenAM Console, navigate to Configure > Server Defaults > Advanced, enter the key name and value, and then click Add.

For additional information on tuning CTS, see xref:../admin-guide/chap-tuning.adoc#tuning-ldap-settings-cts["Tuning LDAP CTS and Configuration Store Settings"] in the __Administration Guide__.
